For goal-driven improvement work, read `references/learning-loop.md` and `slurp/GOALS.md` first. Ask only for missing priorities, save agreed goals and dated learnings there, and resume the next check on later invocations. Keep standalone queries and reports focused on the user’s request.

Read references/learning-loop.md. Inspect actual code and existing events. Produce product context, metric definitions, the smallest useful event mapping, instrumentation changes and tests. Verify collection through Slurp and distinguish accepted events from published archives (`slurp sync --now`, with the admin token, publishes first). Include eligible attempts and failures, stable identity and attempt IDs. Use slurp status, describe, sync and sql --file as needed. Use what the app already has before adding an SDK: a Segment or Sentry SDK only needs its host or DSN changed (see "Instrument and connect" in the slurp skill). To capture what users say in a web app, mount the feedback widget; it sends `feedback` events. Give each source (web, ios, a webhook) its own publishable key (`slurp project key create PROJECT --scope publishable --source ios`) so `sender` tells them apart. Always send an `id` with events that may be retried, since a record without one is a new event each time; the SDKs and `slurp send` do. Check `slurp health` after the first sync for events the import set aside. Credentials stay in secret stores. Human approval precedes production releases.
